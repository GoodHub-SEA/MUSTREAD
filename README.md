# 👋 Welcome to GoodHub SEA's Open Source Community

**GoodHub SEA** is a civic-tech collective that builds and supports open source tools for youth communities, social impact organizations, and nonprofits across Southeast Asia.

This is your onboarding guide as a contributor to our ecosystem of open-source projects. Whether you're a product manager, designer, software engineer, data scientist, or community builder—there's a place for you here.

---

## 🧭 What We Stand For

Inspired by organizations like [Better.sg](https://github.com/bettersg), we believe in:

- **Tech for good**: We build tech that enables changemakers.
- **Southeast Asia first**: We serve our region with cultural and contextual relevance.
- **People over process**: Technology is a means, not an end. We ship things that matter.
- **Open collaboration**: Transparency and open dialogue power better products.

## ✅ What You Should Know Before You Contribute

### 1. Read This First
Each project will have:
- Its own `README.md` for context
- A `CONTRIBUTING.md` outlining contribution flow
- A `CODE_OF_CONDUCT.md` for community expectations

### 2. You Don’t Need to Be a Senior Engineer
Seriously. We welcome first-time contributors and folks from non-technical backgrounds. Whether it’s fixing typos, writing docs, doing QA, or launching features, there’s meaningful work for all.

### 3. We Use GitHub to Collaborate
Please make pull requests (PRs), review issues, and comment on discussions via GitHub. Most of our tech stack includes:
- Web apps (React, TypeScript, Vue)
- Backend APIs (Node.js, Firebase, Python)
- Low-code/No-code platforms (Retool, Airtable)
- Occasionally mobile (Flutter, React Native)

Don’t worry—we’ll guide you through project-specific setups.

## 🛠 Best Practices for Developers

Regardless of tech stack, follow these:

### 🚀 Git & Code Standards
- Use feature branches: `feat/signup-flow`, `fix/button-overlap`
- Commit clearly: `feat: add referral link tracking`
- Keep PRs small and focused
- Include tests or screenshots when possible

### 📚 Document As You Go
- Don’t just code—write. Add comments, update READMEs, or even blog.
- Make your feature discoverable: how can others use or extend it?

### 🔁 Don’t Reinvent the Wheel
Use libraries where possible. Prioritize maintainability and transferability over cleverness.

### 🧪 Test Your Work
If the project has a test framework, write tests. If not, manually test and document how others can replicate your feature.

## 🔍 Pull Request Approval Principles

At GoodHub SEA, we maintain high standards for code quality, readability, and collaboration. Drawing from Rocket Academy’s best practices, here's what we expect from pull requests:

### ✅ What We Look For

| Criteria               | Description                                                                 |
|------------------------|-----------------------------------------------------------------------------|
| **Clarity**            | Code is readable and well-structured. PR title and description clearly explain the _what_ and _why_. |
| **Correctness**        | Code functions as intended and solves the relevant issue without causing regressions. |
| **Scope**              | Focused PRs only. One issue or feature per PR to avoid unnecessary complexity. |
| **Documentation**      | Public-facing features and non-trivial logic must be documented. Update READMEs or inline comments as needed. |
| **Testing**            | PRs should include unit or integration tests. If testing is not feasible, clearly explain how the feature was verified. |
| **Security & Privacy** | Never expose secrets, credentials, or personal user data. Always validate inputs where applicable. |
| **Accessibility**      | For UI changes, support screen readers, keyboard nav, and sufficient contrast. |
| **Performance**        | Efficient logic preferred. No unnecessary loops, queries, or re-renders. |
| **Sustainability**     | Write idiomatic, maintainable code that future contributors can easily understand. Follow DRY principles. |

### 🔄 Review Process

1. **Initial Review**: A maintainer or experienced contributor will be assigned.
2. **Feedback & Revisions**: Expect constructive feedback and suggestions.
3. **Approval Threshold**: Most PRs require **1–2 approvals** before merging.
4. **Merge Strategy**: We use **Squash and Merge** to keep a clean Git history, unless otherwise noted.

### 🧠 Tips for Faster Approval

- Reference issues your PR addresses (e.g., `Closes #123`)
- Include screenshots/GIFs for UI changes
- Provide testing steps or links to deployed previews
- Keep PRs small and focused
- Be responsive and open to feedback

## 🤝 Contributor Workflow

1. **Fork the repo** & clone your fork
2. **Create a feature branch**  
   `git checkout -b feat/my-new-feature`
3. **Make your changes** & commit  
   `git commit -m "feat: implement user feedback modal"`
4. **Push your branch**  
   `git push origin feat/my-new-feature`
5. **Submit a pull request** to the main repo

Tag an issue if your PR addresses one. If unsure, ask in the GitHub discussion or Slack.
